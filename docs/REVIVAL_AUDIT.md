## Executive Summary

AccessRoute is an accessibility-first public transport connectivity platform focused on Chennai and surrounding connected transit corridors (Chengalpattu, Kanchipuram). The project was previously scoped for the HackNova hackathon under the `hacknova-mvp` branch.

The codebase represents a **working hybrid prototype**:
1. **Frontend**: A React 19 / Vite 8 single-page application styled with Tailwind CSS v4 and MapLibre GL. It possesses responsive views (Map, Route Options, Route Details, Journey Steps, Assisted Travel, Travel Preferences, Report Issue modal, and Impact Profile), browser Web Speech API voice input/output, and Google Gemini integration with a deterministic offline fallback.
2. **Backend**: An Express 5 REST API with modular routers (`/api/locations`, `/api/routes`, `/api/stations`, `/api/issues`, `/api/profile`), input validation middleware, error handling, and a dual-layer database client (Supabase PostgreSQL with fallback to an in-memory Chennai seed store).
3. **Core Limitation**: The routing and map visualization currently operate as a **visual and algorithmic simulation over 6 hardcoded Chennai hubs** (`Chennai Central`, `Egmore`, `T. Nagar`, `Koyambedu`, `Guindy`, `Tambaram`). Route polylines are generated by applying a 1D linear stretch (affine interpolation) over pre-baked Chennai Central → Guindy coordinates, rather than computing real multimodal paths across a transit network graph. Furthermore, `JourneySteps.jsx` and `RouteDetails.jsx` have hardcoded step data directly in JSX.
4. **Immediate Security Blocker**: The `.env` file is currently **tracked in Git** (`git ls-files .env` returns `.env`), and `.gitignore` lacks an entry for `.env`. Client-side environment variables (`VITE_GEMINI_API_KEY`) also risk leaking secrets into client browser bundles.

All non-destructive automated test suites currently pass:
- **`npm run test:api`**: 34 / 34 passing assertions.
- **`npm run test:ai`**: 5 / 5 passing assertions.
- **`npm run lint`** (`oxlint`): 0 errors, 43 warnings (mostly from an embedded legacy submodule).
- **`npm run build`**: Production Vite bundle builds successfully in ~4.3 seconds.

### 2.2 Application State Architecture (`AppContext.jsx`)
State is centralized in a single React Context (`AppContext`):
- `currentView`: Controls the active view panel (`'route-options'`, `'route-details'`, `'journey-steps'`, `'assisted'`, `'profile'`, `'preferences'`, `'map'`).
- `origin` / `destination`: Defaults to `'Chennai Central'` and `'Guindy'`.
- `preferences`: Object containing boolean flags (`wheelchair`, `avoidStairs`, `voiceGuidance`, `minimizeWalking`, `limitedMobility`, `audioNavigation`).
- `selectedRouteKey`: Current selection (`'recommended'`, `'fastest'`, `'lowestCost'`).
- `routes`: Initialized to `DEMO_ROUTES`, dynamically refreshed via `searchRoutes()`.
- `userStats`: Commuter statistics initialized to `USER_IMPACT_STATS`.
- `aiRouteExplanation` / `voiceTranscript`: Gemini-generated or template explanations.
- Audio / Speech State: `isPlayingAudio`, `isListeningVoice`, `isAiProcessing`.

**Evaluation**: The context pattern is clean and appropriate for the current MVP scale. However, state is entirely ephemeral (in-memory React state) with no `localStorage` caching or user session persistence.

## 3. Deep Dive: Map & Geographic Routing Reality Check

### 3.1 Base Map Layer
- **Implementation**: `Map.jsx` uses `maplibre-gl` with an open-source raster tile style from CartoDB Voyager (`https://a.basemaps.cartocdn.com/rastertiles/voyager/{z}/{x}/{y}@2x.png`).
- **Verdict**: **Real geographic base map**. The user sees real roads, water bodies, and Chennai landmarks.

### 3.2 Metro Line Overlays
- **Implementation**: `CHENNAI_METRO_LINES` in `src/utils/routing.js` defines two GeoJSON LineStrings:
  - Blue Line (13 points): Chennai Central → Government Estate → LIC → Thousand Lights → AG-DMS → Teynampet → Nandanam → Saidapet → Little Mount → Guindy → Alandur → Meenambakkam → Chennai Airport.
  - Green Line (13 points): Chennai Central → Egmore → Nehru Park → Kilpauk → Shenoy Nagar → Anna Nagar East → Thirumangalam → Koyambedu → CMBT → Ashok Nagar → Ekkattuthangal → Alandur → St. Thomas Mount.
- **Verdict**: **Real geographic coordinates** representing the actual alignment of Chennai Metro Phase 1.

### 3.3 Station & Feature Markers
- **Implementation**:
  - Intermediate nodes on the map are hardcoded to 3 stations: `Egmore Station`, `Saidapet Metro`, `T. Nagar Hub`.
  - Accessibility overlay features (`CHENNAI_ACCESSIBILITY_FEATURES`) are 11 static pins representing elevators, ramps, step-free entrances, and stairs at Central, Egmore, Saidapet, and Guindy.
- **Verdict**: **Static real-world coordinates**, but limited to a small, hand-curated demo subset.

### 3.4 Route Polylines: Real Routing vs. Visual Simulation
- **Implementation in `Map.jsx` (lines 121–147)**:
  ```javascript
  const getTransformedRouteCoords = (baseCoords, startPt, endPt) => {
    // ...
    const defaultOrigin = [80.2707, 13.0827]; // Chennai Central
    const defaultDest = [80.2408, 13.0001];   // Guindy
    // ...
    return baseCoords.map((pt, idx) => {
      const t = totalPts > 1 ? idx / (totalPts - 1) : 0;
      const dx = (1 - t) * startDeltaX + t * endDeltaX;
      const dy = (1 - t) * startDeltaY + t * endDeltaY;
      return [pt[0] + dx, pt[1] + dy];
    });
  };
  ```
- **Implementation in `routing.js` (`getOSRMRoutePath`)**:
  - Makes client-side HTTP calls to the public demo OSRM endpoint (`https://router.project-osrm.org/route/v1/driving/...`).
  - Fetches driving road geometry for a car, **not public transport routes**. It does not model bus stops, bus lines, train timetables, track geometry, or sidewalk pedestrian accessibility.
  - If the OSRM fetch fails or is not applicable, it falls back to the canned `CHENNAI_CANDIDATE_ROUTES` polyline, which is then distorted using the affine delta shift above.
- **Verdict**: **Visual Simulation**. Route polylines are either car-driving roads from public OSRM or an affine geometric distortion of the Chennai Central → Guindy corridor stretched between the selected points. There is **no true multimodal public transit graph engine**.

## 5. Security, Secrets & Deployment Risks

1. **Active Secret Exposure Hazard (`.env` in Git)**:
   - Git tracking check: `git ls-files .env` confirms `.env` is committed and tracked in the repository.
   - `.gitignore` ignores `node_modules`, `dist`, logs, and test results, but does **not** ignore `.env` or `.env.local`.
   - **Remediation**: Add `.env*` to `.gitignore` immediately, untrack `.env` from Git without removing local files (`git rm --cached .env`), and audit commit history for exposed API keys.
2. **Client-Side API Key Leakage**:
   - `src/utils/geminiClient.js` inspects `import.meta.env.VITE_GEMINI_API_KEY`.
   - In Vite, any variable starting with `VITE_` is statically replaced into the client bundle at build time. Anyone visiting the site can extract the Gemini API key via browser DevTools.
   - **Remediation**: All LLM / Gemini operations must be proxied through the Express backend (`POST /api/ai/extract-preferences` and `POST /api/ai/explain-route`).
3. **Overly Permissive CORS**:
   - `backend/server.js` configures `cors({ origin: '*' })`. This is suitable for local hackathon development but insecure for production.
   - **Remediation**: Configure CORS to restrict allowed origins to the authorized frontend domain.
4. **Nested Gitlink Anomaly**:
   - The directory `AccessRoute/` is registered as a Git submodule/tree link (`mode 160000`). It creates confusion, duplicates source files, and pollutes lint checks.
5. **Production Deployment Gap**:
   - The project currently relies on running two separate processes: `npm run dev` (Vite on port 3000) and `npm run server` (Express on port 5000).
   - In production, a unified runner is required: either Express serves the built Vite `dist/` bundle on a single port or frontend and backend are deployed to independent managed services (e.g., Cloudflare Pages/Vercel + Render/Railway).

1. **Transit Datasets (GTFS Static)**:
   - **MTC (Metropolitan Transport Corporation)**: Bus routes, stop catalogs, trips, and stage fares for Chennai and Chengalpattu corridors.
   - **CMRL (Chennai Metro Rail Limited)**: Blue Line (Airport to Wimco Nagar), Green Line (Central to St. Thomas Mount), and upcoming Phase 2 alignment data.
   - **Southern Railway (Suburban/Local Trains & MRTS)**: Chennai Central – Arakkonam, Chennai Central – Gummidipoondi, Chennai Beach – Tambaram – Chengalpattu, and Chennai Beach – Velachery (MRTS).
2. **Pedestrian & Accessibility Geodata**:
   - OpenStreetMap (OSM) pedestrian network tagged with `wheelchair=yes|no|limited`, `incline=*`, `curb=*`, `tactile_paving=*`, and `crossing=traffic_signals`.
3. **Multimodal Routing Engine**:
   - Current codebase lacks a graph router. AccessRoute requires a schedule-aware multimodal router such as OpenTripPlanner 2.x, GraphHopper, or a lightweight Node.js/Python RAPTOR (Round-Based Public Transit Routing) implementation that evaluates timetable transfers and accessibility penalties.
4. **Real-time Vehicle Positions (GTFS-RT)**:
   - Ingestion of live vehicle feeds for MTC buses and Metro train status via GTFS-RT (VehiclePositions, TripUpdates, ServiceAlerts) exposed via WebSocket or Server-Sent Events (SSE).
5. **Persistence Layer**:
   - PostgreSQL with **PostGIS** extension to support spatial queries (`ST_DWithin`, `ST_Distance`, `ST_Contains`) for finding nearby stops, stations, and active civic hazards.

### Phase 01: Repository Cleanliness, Security Hardening & Secret Isolation
- Add `.env`, `.env.local`, and `*.local` to `.gitignore`.
- Remove `.env` from Git index (`git rm --cached .env`) without deleting local files.
- Move Gemini AI preference extraction and route explanation from `src/utils/geminiClient.js` to dedicated backend endpoints (`/api/ai/extract` and `/api/ai/explain`).
- Remove `leaflet` and `react-leaflet` from `package.json`.
- Resolve or ignore the nested `AccessRoute/` submodule to eliminate 30+ lint warnings.

### Phase 02: Chennai Geographic Expansion & True Station Geodatabase
- Replace the 6-hotspot hardcoding with a comprehensive Chennai geodatabase:
  - All 40+ operational Chennai Metro stations (Blue and Green Lines).
  - Major suburban railway stations (Chennai Beach to Chengalpattu, Central to Tiruvallur/Gummidipoondi).
  - Major MTC bus depots (Broadway, CMBT, Adyar, Tambaram, Poonamallee, T. Nagar).
- Implement backend `/api/locations/search?q=` with fuzzy search and station category filtering.
- Update `RouteSearch.jsx` to dynamically query this endpoint, preserving voice input compatibility.

### Phase 03: Transit Timetable Ingestion & True Multimodal Routing
- Ingest GTFS static data for Chennai Metro and Southern Railway Suburban lines.
- Implement an accessible routing engine:
  - Calculate valid multi-leg journeys (Walk → Metro → Walk, Walk → Bus → Train).
  - Use exact Metro track geometry and road-snapped bus corridors instead of affine coordinate stretching.
  - Compute realistic travel times based on headway and transfer walking buffers.
- Provide real GeoJSON coordinates for all candidate routes so `Map.jsx` displays true paths.

### Phase 04: Dynamic Journey UI & CityPulse Civic Layer
- Refactor `JourneySteps.jsx` to dynamically render steps from `selectedRoute.segments` rather than static JSX.
- Refactor `RouteDetails.jsx` to bind directly to the active route's calculated metrics.
- Upgrade `ReportIssue.jsx` into the **CityPulse** civic reporting engine:
  - Store reported issues (potholes, broken elevators, blocked ramps) with GPS coordinates.
  - Expose `GET /api/issues/active` to render interactive warning markers on `Map.jsx`.
  - Feed active civic disruptions back into the routing engine to apply routing penalties to affected stations or paths.

### Phase 05: Personal Mobility Dashboard & Gamification
- Refactor `Profile.jsx` from static mock data to dynamic state:
  - Persist user journey history in database/localStorage.
  - Calculate actual commuter savings against dynamic cab fare formulas (`₹50 base + ₹16/km`).
  - Calculate actual CO2 reduction based on transit modes used (`~120g CO2/km avoided vs. petrol car`).
- Introduce civic points and badges for verified public transit trips and confirmed infrastructure reports.

### Phase 06: Live Vehicle Positions (GTFS-RT) & Ticketing Research
- Implement GTFS-RT ingestion worker for live MTC bus coordinates and CMRL train headways where public APIs or authorized partner feeds exist.
- Stream live positions to `Map.jsx` using SSE or WebSockets with smooth marker interpolation.
- Conduct architecture and regulatory research into unified QR ticketing (ONDC / Beckn mobility protocols, CMRL QR integration).
